## 1. 当初の要望とプロジェクトの目的

### 1.1 つくるもの・目指すゴール
最終的には **「bot・AI チーム・カンバンタスク」** を統合的に回せる開発基盤を目指しつつ、現在それらを満足な形で備えた既存アプリケーションが存在しないため、まずはその中核となる **「実際に日常利用できる、ファイル操作・テスト実行が可能な自作コーディングエージェントエンジン」** をプロトタイピングし、自作の実現可能性と到達水準を実証する（根拠: `docs/01_idea.md`）。

### 1.2 当初から求められている主要特性
1. **OS 構造を参考にした「防波堤カーネル」設計**:
   - カーネル自体はエージェントループ（思考ループ）を持たず、**システムコール（Syscall）の調停・権限制御・監査を担う防波堤** に徹する。
   - エージェントループは非特権のユーザー空間プロセスとして動作し、ファイル操作・VCS 操作・外部コマンド実行・LLM 推論をすべてシステムコールとしてカーネルへ要求する。保護リングのレベルに応じて、危険な操作や確定操作の前に人間の許可確認を挟む。
2. **モジュラーシステム**:
   - コア本体は最小限の機構に保ち、LLM プロバイダ、システムコール（ツール）、フック（インターセプタ）、スキルといった要素を着脱・拡張しやすい構造にする。
3. **プロンプト入力ごとのプロバイダ／モデル切替**:
   - `Local Ollama`（API キー不要で手軽な開発検証が可能）、`Ollama Cloud`、`OpenRouter` に対応し、人間のプロンプト入力ごとにプロバイダとモデルを容易に切り替えられる UX と内部表現を備える。
4. **可観測性（監査ログと KV キャッシュ監視）**:
   - 全システムコールを `strace` 相当の構造化監査ログに残す。
   - LLM API の入出力に加え、コストと応答速度を大きく左右する **プロンプトキャッシュ（KV キャッシュヒット量・ヒット率）** を数値で監視・記録する。
5. **ACP（Agent Client Protocol）による上位 UI の切り離し**:
   - エンジン本体は ACP インターフェースから下の層に専念させ、検証・対話操作用の軽量な **簡易 ACP CLI クライアント** を同梱する。
6. **Dart + Windows ネイティブ実行環境**:
   - 型厳格かつフォーマッターが整った Dart で実装し、Windows Native DLL（Win32 API）連携を活用しつつ、`dart compile exe` で単一実行ファイル（`.exe`）へビルドできる構成とする。

## 2. 背景課題：先行試作での「3つの暗礁」と既存エージェントの限界

従来のモノリシックなコーディングエージェントや先行試作において、「LLM 対話ループ・ツール実行・権限制御・コンテキスト圧縮・Git 操作・UI 状態」を密結合させた結果、以下の **3大暗礁** が同時に噴出して座礁要因となっていた（根拠: `docs/references/agent_kernel_plan/00_index.md`, `05_three_walls_and_step_plan.md`）。

1. **暗礁 1：権限の混線と危険操作の暴発**
   - 複数タスクや自律ループの中で承認確認が混線したり、LLM が事前学習の手癖で生の `git checkout` / `git stash` や破壊的シェルコマンドを叩いて人間の作業ツリーを壊すリスクがある。
2. **暗礁 2：コンテキスト溢れと KV キャッシュ崩壊**
   - 巨大ファイルや大量の検索・テスト出力を 1 回読んだだけでコンテキスト窓が溢れて停止する。また素朴なプロンプト先頭書き換えや安易な LLM 要約を入れると、KV キャッシュ（Exact Prefix Match）が毎ターン無効化され、重要行番号の喪失による再読込スラッシングを引き起こす。
3. **暗礁 3：ファイル編集の衝突と作業状態破壊**
   - 人間が未コミット変更を持っている状態でエージェントが編集すると変更が混ざり、テスト失敗時に元へ戻せない。かといってインメモリ仮想ファイルシステムを自作すると、`dart test` 等の外部 OS プロセスとの同期で泥沼化する。

## 3. 対象利用者

- **主対象者**: エージェントエンジンを開発・検証し、自身のローカル開発リポジトリ（Jujutsu `jj` 管理下）で日常的なコード読解・機能実装・テスト実行に用いる **開発者本人（プロトタイプ検証者）**。
- **将来の上位接続先**: ACP（JSON-RPC 2.0 over `stdio`）に対応する外部エディタ（Zed 等）や将来構築するカンバン／AI チーム UI（Stage 1 では同梱の簡易 ACP CLI クライアントを直接の操作窓口とする）。

## 4. 解決アプローチと今回の計画（Stage 1）の狙い

### 4.1 「OS カーネル原則 × Jujutsu (`jj`) ネイティブ」による突破
自作の複雑な OverlayFS を組む代わりに、ワーキングコピーの自動スナップショット（`@`）・Operation Log による原子的ロールバック（`jj op restore`）・無名チェンジ分離（`jj new`）を標準搭載する **Jujutsu (`jj`)** を最初からカーネルの CoW トランザクション基盤（`JjDriver`）として採用する。さらに複雑さの組み合わせ爆発を防ぐため、開発全体を **3 Stage × 3 Step** に分割し、「1 ステップにつき新しい複雑さは 1 軸だけ入れる」直交ステップ方針をとる（根拠: `docs/02_development_step.md`）。

### 4.2 Stage 1 の狙いと安全ロック
本計画（`plan_20261119_stage1_kernel_agent`）は **Stage 1 全体（Step 1-1・Step 1-2・Step 1-3）** を対象とする。
- **Stage 1 のゴール**: マルチプロセスの複雑さを持ち込む前に、「カーネル＝システムコール層（＋I/O キャップ）」「3 プロバイダ対応・毎ターンモデル切替」「`strace` 監査・キャッシュ監視」「`jj` による人間の作業を汚さない安全な編集と 1 発ロールバック」「Windows Job Object による外部プロセス一括強制終了」「ACP 分離・保護リング承認ゲート・単一 `.exe` 化」を貫通させ、**日常的に使える安全な `jj` ネイティブ・シングルコーディングエージェント** を完成させる。
- **意図的な安全ロック**: Stage 1 では **シングルプロセス固定** とする（複数エージェント間の同時編集競合や承認ダイアログ混線を原理的にゼロにし、単一エージェントとしての防波堤とトランザクション基盤を固める）。ただし Stage 2・Stage 3 へ進む際に手戻りにならないカーネル境界（`SyscallGate` 単一通過、Canonical IR、PCB / Ring 構造、ドライバ抽象）は Stage 1 から確立する。

## 5. 当初の仮説と技術的不確実性

Stage 1 のプロトタイピングを通じて検証・解消したい主な仮説と不確実性は以下の通りである。

| # | 仮説 | 伴う技術的不確実性・確認点 |
| :--- | :--- | :--- |
| **H-1** | **Canonical IR によるプロバイダ透過切替**: 会話とツール履歴をプロバイダ非依存の中間表現で保持し、システム定義先頭を不変に保てば、`Local Ollama`・`OpenRouter`・`Ollama Cloud` 間で毎ターン切り替えても履歴破損（State Spill）を起こさず、同一モデル連続時には KV キャッシュヒットが向上する。 | 各プロバイダ（特に `Ollama Cloud` や `Local Ollama`、OpenRouter 上の各モデル）における Tool Call 形式の細部差異と、レスポンス内の `cached_tokens` 等の統計フィールド仕様・発火条件の差異。 |
| **H-2** | **`jj` ネイティブ分離と Hook による安全編集**: `JjDriver` が `jj new` で作業チェンジを切り、Anti-Git-Habit Hook で生の `git`/`jj` 実行を遮断して誘導すれば、LLM の Git 手癖バイアスを抑え込み、人間の直前作業（`@-`）を一切汚さず編集〜ロールバック・`squash` を回せる。 | `jj` CLI（ローカル導入版）における `--ignore-working-copy` 参照と、ファイル直接編集後の自動スナップショット更新・`jj diff` 取得・非対話 `squash` / `op restore` の正確な挙動整合。 |
| **H-3** | **I/O キャップと Windows Job Object による一撃死・ゾンビ根絶**: カーネル層で全システムコール出力サイズを強制キャップし、`sys_exec` を Win32 Job Object で包めば、巨大ファイルによるコンテキスト一撃死も、タイムアウト時の孫プロセス残留も防げる。 | `dart compile exe`（AOT バイナリ）環境下での Win32 Job Object FFI 呼び出し、および親プロセス自身が既存 Job Object 配下にある端末環境でのネスト動作。 |
| **H-4** | **ACP `stdio` 分離と Ring 2 承認ゲートの実用性**: エンジンを JSON-RPC 2.0 over `stdio` で分離し、仮編集は即時許可・確定 `squash` や要注意コマンドのみ `WAITING_APPROVAL` で人間確認を求めれば、安全性を保ちつつテンポの良い対話体験が得られる。 | ACP プロトコル仕様におけるモデル切替・リアルタイム通知・Permission 要求メッセージの具体的なワイヤ表現と、`stdio` ストリームへの不要ログ混入防止。 |
