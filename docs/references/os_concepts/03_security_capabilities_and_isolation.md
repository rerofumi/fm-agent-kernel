# 3. セキュリティ・ケーパビリティ・隔離・資源制御

「危険な操作をカーネルがどう抑止するか」「子プロセスに権限と予算をどう配分するか」に関する OS の設計パターンをまとめる。

---

## 3.1 古典的アクセス制御（DAC / MAC）の限界

- **DAC (Discretionary Access Control / 任意アクセス制御)**:
  - UNIX の `rwx`（所有者・グループ・その他）や ACL。
  - **欠点**: プロセスは「実行ユーザーの持つ全権限」をそのまま継承する。これを **Ambient Authority（暗黙の権限）** と呼ぶ。例えばユーザーが起動した電卓アプリやツールが、ユーザーの SSH 鍵や全ソースコードを読み書きできてしまう。
- **MAC (Mandatory Access Control / 強制アクセス制御)**:
  - SELinux, AppArmor, SMACK, Windows Integrity Levels。
  - システム全体のポリシー管理者（セキュリティラベルやパスルール）が、ユーザーやプロセスごとの行動範囲を強制制限する。
  - **欠点**: ポリシー記述が複雑・巨大化しやすく、動的に生成されるサブプロセスやタスクごとに柔軟な一時権限を付与する用途（委譲）には向きにくい。

---

## 3.2 ケーパビリティベース・セキュリティ（Capability-based Security）

「あなたが誰か（Identity）」ではなく「あなたがどの鍵（Capability）を持っているか」でアクセスを検証する設計思想。

### 核心原則
1. **Unforgeable Token（偽造不能な参照）**: ケーパビリティは「対象オブジェクトへの参照」と「許可された操作（Rights: 読取・書込・実行・複製・委譲等）」を不可分に束ねたトークンであり、プロセスが勝手に生成・改ざんできない（カーネルがプロセスごとのテーブルで管理する）。
2. **Zero Ambient Authority（暗黙の権限のゼロ化）**: プロセスが明示的に渡されたケーパビリティ以外の資源は「そもそも名前空間に存在しない」ためアクセスできない。
3. **Confused Deputy（混乱した代理人）問題の解消**: 権限の高いサーバーに「このパスに書いて」と頼むと悪用される問題に対し、「パス文字列」ではなく「権限付きハンドルそのもの」を渡すことで、依頼者自身が持っていた権限の範囲内でしか実行できなくする。
4. **Attenuation（権限の減衰）と委譲**: 親は自分が持つ Read+Write ケーパビリティをコピーする際、Write 権を削って **Read-Only にしてから子に渡す** ことができる。子は親以上の権限を決して得られない。
5. **Revocation（失効・取り消し）**: 一度渡したケーパビリティを後から無効化したい場合、間に **Membrane（膜）や Revocable Forwarder（中継プロキシオブジェクト）** を挟み、親側で中継を閉じることで一括取り消しを実現する（KeyKOS / EROS / seL4 の CNode 派生ツリー）。

### 代表的な実装例
- **KeyKOS / EROS / CapROS**: 永続的（Persistent）な純粋ケーパビリティ OS。全システム状態を定期的にチェックポイントし、電源断後も同じ状態・同じケーパビリティ構造で再開できる。
- **seL4**: CSpace（Capability Space）と呼ばれる木構造テーブルで全資源（メモリ・スレッド・エンドポイント）への権限を管理。`Mint` 操作で権限を減衰させた子ケーパビリティを作成可能。
- **Fuchsia / Zircon**: `zx_handle_t` とビットマスク `zx_rights_t`。チャネル経由でハンドルを他プロセスへ送受信。
- **FreeBSD Capsicum**: 既存 UNIX アプリを段階的にケーパビリティ化するための実用機構。`cap_enter()` を呼ぶとプロセスは **Capability Mode** に入り、`open()` などのグローバル名前空間を辿るシステムコールが一切禁止され、事前に開いたディレクトリ FD に対する `openat()` 等のみが許される。
- **WASI (WebAssembly System Interface) Preview 2 / Component Model**: ゲストモジュールにグローバル FS を渡さず、事前開済みのディレクトリハンドルや抽象リソース（Capabilities）をインポートとして注入する。

## 3.3 階層的・再帰的リソース管理（Genode モデル）

多くの OS は「システム全体のグローバルな資源プール」から各プロセスに割り当てるが、**Genode OS Framework** は完全な木構造による再帰的委譲を採用している。

- **親が子の環境（World）を完全に定義する**: 子プロセスにとって、親は疑似カーネルのように振る舞う。子がファイルやネットワークやメモリを使うとき、すべて親経由で **Session（セッション）** を開く。
- **資源の寄贈（Quota Donation）**:
  - 親は自分の持つ RAM・CPU 予算の一部を切り出して子に割り当てる。
  - 子がさらにサーバー（例: FS サーバー）にサービスを要求する際は、サーバーがメモリ不足で落ちないよう **依頼者（子）が自分のクオータから必要メモリをサーバーへ寄贈** する。
- **再帰的ネストと回収**: 子が孫を作る場合も自分の予算の範囲内でしか作れない。親が子プロセスを終了させると、その配下（孫や寄贈済みセッション）に紐づく全資源が漏れなく回収される。

## 3.4 コンテナ・サンドボックス・リソース制限技術

### リソース制限の諸機構
- **POSIX `rlimit` (`setrlimit`)**: プロセス単位のソフト/ハード上限（最大 CPU 時間 `RLIMIT_CPU`、最大開ファイル数 `RLIMIT_NOFILE`、最大プロセス数 `RLIMIT_NPROC`、仮想メモリ上限 `RLIMIT_AS` 等）。
- **Linux `cgroups` (Control Groups v1 / v2)**: プロセスグループ（木構造）単位でリソースの **制限（Limit）・保証（Reservation）・アカウンティング（Accounting）** を行う。
  - `cgroups v2` では単一階層ツリーに統一され、CPU 時間、メモリ上限（`memory.max` / `memory.high`）、PID 数（`pids.max`）、I/O 帯域を一貫して制御できる。
  - 子プロセスをどれだけ spawn しても親 cgroup の合計予算を超えられない。

### 名前空間・システムコール制限による隔離
- **chroot / FreeBSD Jail / Solaris Zones**: ファイルシステムルートやプロセス視界・ネットワークを閉じ込める初期〜中期の OS レベル仮想化。
- **Linux Namespaces**: 以下の 8 種の視界をプロセス単位で独立させる（コンテナの基盤）。
  - `mnt` (マウント点), `pid` (プロセス ID 空間 — 子からは自分が PID 1 に見える), `net` (ネットワークスタック), `ipc`, `uts` (ホスト名), `user` (UID/GID マッピング — 非特権ユーザーがコンテナ内で root になれる), `cgroup`, `time`。
- **`seccomp-bpf` (Linux)**: プロセスが発行できるシステムコールと引数の値を eBPF プログラムでフィルタリングする（許可・拒否・`ENOSYS` 返却・ユーザー空間通知 `SECCOMP_RET_USER_NOTIF`）。
- **OpenBSD `pledge` & `unveil`**:
  - `pledge("stdio rpath ...")`: プロセス自身が初期化後に「以降自分が使う操作カテゴリ（約束事）」を宣言し、それ以外を呼んだら即座にプロセスを強制終了する。**自己宣言型の権限縮減**。
  - `unveil("/path", "rw")`: プロセスから見えるファイルシステムパスを特定のディレクトリ・権限だけに限定する。
- **Linux Landlock**: 非特権プロセスが自分自身（および子孫）のファイルアクセスやネットワーク操作をサンドボックス化できる LSM（Linux Security Modules）。`pledge`/`unveil` に近い使いやすさを目指している。

### システムコール横取り（Interception）とマイクロ VM
- **ユーザー空間カーネル / `ptrace` / gVisor**:
  - アプリケーションが発行したシステムコールをホストカーネルに直接渡さず、中間層（Sentry 等）がすべてインターセプトしてエミュレート・検査する。攻撃対象面を劇的に減らせるが、システムコール頻発時にオーバーヘッドがある。
- **MicroVM（Firecracker / Cloud Hypervisor / Kata Containers）**:
  - 仮想化支援機構（KVM 等）を使い、最小限のデバイスエミュレーション（Virtio のみ等）で軽量 VM を数ミリ秒〜百ミリ秒で起動。強固なハイパーバイザ境界を得る。
- **Qubes OS（Compartmentalization）**:
  - 「完璧な単一 OS」を諦め、用途ごと（仕事・個人・非信頼ダウンロード・ネットワーク処理・USB 処理）に別々の軽量 VM（Qube）を割り当て、ハイパーバイザ（Xen）と厳格な RPC（qrexec）および GUI 分離で統合するデスクトップ OS。
