# 1. カーネルアーキテクチャの類型と歴史的系譜

OS の中核であるカーネルが「何を自ら引き受け、何を外部（ユーザー空間や別コンポーネント）に出すか」は、OS 設計における最大の分岐点である。

---

## 1.1 黎明期〜古典的アーキテクチャ

### バッチ処理・初期タイムシェアリング（CTSS, OS/360）
- **特徴**: 初期のモニタ／バッチシステムから、複数のジョブをメモリに常駐させて切り替えるマルチプログラミングへ発展。
- **設計上の意味**: 割り込み（Interrupt）、特権命令、システムコール（SVC: Supervisor Call）という「ユーザーと特権層の境界」が確立された。

### モノリシックカーネル（Monolithic Kernel）
- **代表例**: UNIX (V6/V7), Linux, FreeBSD/OpenBSD/NetBSD, Solaris, 初期 DOS/Windows 9x
- **構造**: プロセス管理、メモリ管理、VFS、各種ファイルシステム、ネットワークスタック、デバイスドライバがすべて単一の特権アドレス空間（Kernel Space）で動作する。
- **拡張機構**: 多くの現代的モノリシックカーネルは **LKM (Loadable Kernel Modules)** を備え、実行時にカーネルモジュールを動的にロード・アンロードできる（例: Linux `.ko`）。ただしロードされたモジュールもカーネル空間のフル権限を持つため、1 つのドライバのバグがシステム全体をパニックさせる。
- **利点**: サブシステム間の通信が単なる関数呼び出しであり非常に高速。全体として実装や最適化がしやすい。
- **欠点**: **TCB (Trusted Computing Base: 信頼境界内のコード量)** が巨大になり、障害隔離が弱い。

### 階層型アーキテクチャ（Layered Architecture）
- **代表例**: THE Multiprogramming System (Dijkstra, 1968), Multics, OS/2 の一部概念
- **構造**: OS を厳密な階層（Layer 0: ハードウェア割り込み・スケジューラ → Layer 1: メモリ管理 → Layer 2: コンソール I/O → ... → 最上位: ユーザープログラム）に積み上げ、各層は下位層のみに依存・呼び出し可能とする。
- **利点**: 依存関係が非循環（DAG/線形）となり、設計・デバッグ・正当性検証が容易。
- **欠点**: 現実の OS では循環的な依存（例: 仮想記憶のスワップはファイルシステム/ディスクドライバを使い、ディスクドライバはメモリ割り当てを使う）が発生しやすく、また層をまたぐたびにオーバーヘッドが生じる。

## 1.2 マイクロカーネルの進化

### 第1世代マイクロカーネル（Mach, Chorus）
- **代表例**: CMU Mach (2.5/3.0), ChorusOS
- **思想**: 「メカニズム（機構）とポリシー（方針）の分離」。カーネルには最小限の抽象（Task, Thread, Port, Virtual Memory の一部）のみを残し、ファイルシステムやネットワーク、UNIX 互換層などをユーザー空間サーバー（Personality）として実装。
- **課題**:
  - ハードウェア境界をまたぐ IPC とコンテキストスイッチが頻発し、システムコール性能が大きく低下した。
  - 当初の Mach は「最小」を目指しつつも機能が肥大化し、メモリコピーや柔軟すぎる抽象のコストが重かった。
  - その反動として、現実解としての「ハイブリッドカーネル」や、Mach の失敗を分析した「第2世代マイクロカーネル」が生まれた。

### ハイブリッドカーネル（Hybrid Kernel）
- **代表例**: Windows NT (Executive + Microkernel 層 + HAL), macOS / XNU (Mach + BSD + I/O Kit), DragonFly BSD（一部サーバー機能のスレッド化）
- **構造**: 概念上はマイクロカーネル的なモジュール分離やメッセージパッシング（例: Windows NT の LPC/ALPC やクライアント・サーバー構造、XNU の Mach と BSD の統合）を持ちながら、性能要件からドライバやファイルシステム、グラフィックスの一部などをカーネルアドレス空間に同居させる実用的折衷案。
- **教訓**: 「論理的なレイヤ分離・抽象化」と「物理的なアドレス空間分離（コストの大きい保護境界）」は切り分けて考えることができる。

### 第2世代・第3世代マイクロカーネル（L4, QNX, MINIX 3, seL4, Zircon）
- **代表例**:
  - **L4 系** (L3/L4, Fiasco.OC, L4Re, NOVA): Jochen Liedtke による再設計。「IPC の高速化」を最優先とし、カーネル内のバッファリングや不要な抽象を削ぎ落とした。**「ある概念がカーネル内に置かれるべきなのは、それをカーネル外に移すとシステムの必須機能が実現できない場合だけである（Minimality Principle）」** という基準を提唱。
  - **QNX Neutrino**: 商用リアルタイムマイクロカーネル。すべてがメッセージパッシング（`MsgSend`/`MsgReceive`/`MsgReply`）で結合され、ドライバやファイルシステムも単なるユーザープロセス。プロセス再起動で自己修復が可能。
  - **MINIX 3**: 高い自己修復性（Reliability）に焦点。**Reincarnation Server** がドライバやサーバーを監視し、クラッシュ時に自動的に再起動・置換する。ドライバへの権限は最小限（I/O ポートやメモリの限定範囲のみ）。
  - **seL4**: 第3世代の代表格。機能実装の正当性および情報フロー制御が **数学的に形式検証（Formal Verification）** された初の汎用マイクロカーネル。ケーパビリティベースで、動的メモリ割り当てをカーネル内で行わずユーザー空間に資源管理を委ねる（Untyped Memory モデル）。
  - **Zircon (Google Fuchsia)**: オブジェクトケーパビリティ（Kernel Objects + Handles + Rights）を徹底した現代的マイクロカーネル。グローバル名前空間を持たず、暗黙の権限（Ambient Authority）を排除。

## 1.3 カーネルの再定義・革新的アーキテクチャ

### エグゾカーネル（Exokernel）
- **代表例**: MIT Aegis, Xok, Nemesis
- **思想**: 従来のカーネル（モノリシックもマイクロも）は、固定的な抽象（ファイル、仮想メモリ、ソケットなど）を全アプリに押し付けている。エグゾカーネルは **「抽象化を一切行わず、ハードウェア資源の安全な多重化（保護と割り当て）だけを行う」**。
- **構造**:
  - カーネルは資源の所有権の検証と物理資源の安全な時間・空間分割のみを担当。
  - ファイルシステムやスケジューリング、ネットワークプロトコルなどの OS 抽象は、アプリ側にリンクされる **LibOS (Library OS)** が自由に実装する。
- **示唆**: 「カーネル＝安全境界（防波堤）と資源調停だけ」「実際の振る舞いや抽象＝上位のモジュール/プロセスが好きに組める」という分離の極北。

### マルチカーネル（Multikernel）
- **代表例**: Barrelfish (ETH Zurich / Microsoft Research)
- **思想**: メニーコア・異種コア時代において、カーネル内の共有メモリ＋ロックによるスケーリング限界を打破するため、**「1台のマシンを分散システムとみなす」**。
- **構造**:
  - 各 CPU コア上で独立した小さなカーネルインスタンスが動作し、グローバルな共有データ構造を持たない。
  - コア間の状態同期（ページテーブル更新やスケジューリング協調など）はすべて非同期メッセージパッシングとレプリケーションで行う。

### 言語ベース OS・単一アドレス空間 OS（Language-Based OS / SASOS）
ハードウェア MMU やリング切り替えのコストを避け、**プログラミング言語の型システム・メモリ安全性・コンパイラ検証** によって隔離と保護を実現する系譜。

- **Singularity / Midori (Microsoft Research)**:
  - 単一アドレス空間上に **SIP (Software Isolated Processes)** を配置。
  - 型安全な言語（Sing#）により他プロセスのメモリへの不正ポインタ生成をコンパイル時に不可能にする。
  - プロセス間は共有メモリを一切使わず、**契約（Contract）付きチャネル** による所有権移動（Zero-copy メッセージ送信）のみで通信。
  - 実行前に **マニフェスト（Manifest）** で依存・権限・契約を静的検証。
- **Theseus OS**:
  - Rust の所有権・ライフタイム・型安全性を OS 設計に持ち込んだ **Intralingual OS**。
  - 最大のテーマは **State Spill（状態漏出）と Fate-Sharing（運命共同体化）の根絶**。あるコンポーネントの内部状態が別コンポーネント（やグローバルテーブル）に漏れ出すと、単一モジュールの再起動やホットスワップができなくなる。
  - OS を **Cell（セル）** と呼ばれる小さなモジュールに分割し、明示的インターフェースと所有権追跡によって、実行中でも任意のセル（ドライバやスケジューラ等）を安全に停止・置換（Live Evolution）できる。
- **Asterinas (Framekernel)**:
  - モノリシックの速度とマイクロカーネルの最小 TCB の両立を狙う **Framekernel** アーキテクチャ。
  - 単一のカーネル空間で動作しつつ、内部を **OS Framework (OSTD)**（低レベル操作と `unsafe` を閉じ込めた小さな TCB）と **OS Services**（Safe Rust のみで書かれたドライバや FS）に論理分離する。
  - 言語の安全性境界を「アーキテクチャ境界」として扱う新しい設計。

### ユニカーネル / ライブラリ OS（Unikernel）
- **代表例**: MirageOS (OCaml), OSv, Unikraft, IncludeOS, Nanos
- **構造**: アプリケーションと必要な OS 機能（ネットワーク、ドライバ、スケジューラ等）だけを 1 つの単一アドレス空間イメージに静的リンクし、ハイパーバイザ（KVM/Xen/Firecracker）上で直接動かす。
- **利点**: 不要な汎用 OS 機能（マルチユーザー、シェル、不要な syscall）が一切ないため、起動が数ミリ秒・攻撃対象面が極小・実行効率が極めて高い。
- **欠点**: 単一アプリ前提であり、動的なマルチプロセス環境や対話的デバッグには不向き。

### カーネル内サンドボックス拡張 VM（eBPF）
- **代表例**: Linux eBPF (extended Berkeley Packet Filter)
- **思想**: カーネルを再コンパイル・LKM ロードすることなく、ユーザーが安全にカーネルの振る舞いをプログラム（拡張）できる仕組み。
- **構造**: バイトコードをロード時に **Verifier（静的検証器）** が検査し、「無限ループしない（必ず終了する）」「許可されたメモリ以外に触れない」「境界外アクセスしない」ことを証明した上で JIT コンパイルして実行する。
- **示唆**: プラグインやフックをカーネル／本体に安全に差し込むための「検証可能なサンドボックス実行層」の好例。

## 1.4 比較サマリー

| アーキテクチャ | 隔離手段 | TCB サイズ | 通信コスト | 主な強み | 主な弱み |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **モノリシック** | User/Kernel 境界のみ | 巨大 | 極小（関数呼出） | 高性能・成熟した実装 | ドライバ障害が全体に波及 |
| **マイクロカーネル** | MMU / IPC / Capability | 極小 | 中〜大（境界越え） | 耐障害性・最小権限・検証性 | IPC 設計が悪いと遅い |
| **ハイブリッド** | 論理分離（物理は一部同居） | 大〜中 | 小〜中 | 実用性能と構造化のバランス | 境界が曖昧になりやすい |
| **エグゾカーネル** | ハードウェア資源の多重化 | 極小 | 小（LibOS 内完結） | アプリ特化の極限の自由度 | LibOS 開発の複雑さ |
| **言語ベース / Framekernel** | コンパイラ・型・所有権 | 小（unsafe 層のみ） | 極小（同一空間） | ゼロコピー＋軽量プロセス＋ホットスワップ | 言語とツールチェーンへの強い依存 |
| **ユニカーネル** | ハイパーバイザ（VM 境界） | 小 | 極小 | 極小攻撃面・高速起動 | 汎用マルチプロセス不向き |
