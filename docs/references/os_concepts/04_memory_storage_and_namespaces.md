# 4. 仮想記憶・名前空間・VFS・トランザクションとロールバック

「有限の記憶容量（文脈）をどうやりくりするか」「外部資源をどう統一的に見せ、変更を安全に保留・巻き戻すか」に関する OS の知恵を整理する。

---

## 4.1 仮想記憶とページングの諸概念

物理メモリ（高速・高価・有限）と二次記憶（低速・大容量）のギャップを埋めるために OS が発展させた概念群。

### 基本構造と性能現象
- **ページング (Paging) とページテーブル**: 論理アドレス空間を固定サイズ（例: 4KB）の「ページ」に分割し、物理フレームに動的にマップする。連続した論理空間が、物理的には不連続でも構わない。
- **TLB (Translation Lookaside Buffer) とキャッシュ**: アドレス変換結果をキャッシュする高速領域。コンテキストスイッチ時にアドレス空間が切り替わると TLB フラッシュ（または ASID/PCID タグ付け）が起きる。
- **デマンドページング (Demand Paging)**: 起動時に全データを読み込まず、実際にアクセスされた瞬間（Page Fault）に必要なページだけを読み込む遅延ロード。
- **ワーキングセットモデル (Working Set, Peter Denning)**: ある時間窓 $\Delta$ の間にプロセスが実際に頻繁参照しているページ集合。メモリにワーキングセット全体が収まっている間は高効率だが、下回ると **スラッシング (Thrashing)**（ページ入れ替えばかり起きて実処理が進まない状態）に陥る。

### ページ置換アルゴリズム（Eviction Policies）
有限のフレームが満杯になったとき「どれを追い出す（Evict）か」の戦略。
- **Optimal (Belady's MIN)**: 「未来で最も長く使われないページ」を追い出す理論上の最適解（比較基準）。
- **FIFO**: 最も古く入れたものを追い出す（実装は簡単だが、頻繁に使うものも消えうる・Belady の異常）。
- **LRU (Least Recently Used)**: 最も長い間使われていないものを追い出す。時間的局所性（Temporal Locality）に優れるが、純粋なスキャン（1回だけの全走査）でキャッシュが汚染されやすい。
- **Clock / Second Chance**: 参照ビット（Accessed Bit）を巡回し、1 なら 0 に落として猶予を与え、0 なら追い出す（LRU の低コスト近似）。
- **2Q / LRU-K / ARC (Adaptive Replacement Cache) / S3-FIFO**:
  - 「1回だけ参照されたデータ（Scan）」と「繰り返し参照されるホットデータ（Frequency）」を別キューで管理し、頻度（LFU）と新しさ（LRU）を自動バランスする現代的手法。
- **Dirty Page 管理と Write-back**: 変更されていないページ（Clean）はそのまま破棄できるが、変更されたページ（Dirty）は退避（要約・外部保存）してから追い出す必要がある。
- **メモリ圧縮 (zram / zswap)**: ディスクに逃がす前に、RAM 上で古いページを圧縮して保持し、展開コストと容量のトレードオフを取る。

### Copy-on-Write (CoW)
- データをコピーする際、即座に物理複製せず「同じ物理ページを読み取り専用で共有」し、どちらかが書き込もうとした瞬間（Write Fault）に初めてそのページだけを複製する。
- **応用**: UNIX `fork()` の高速化、仮想マシンスナップショット、不変データ構造。

## 4.2 仮想ファイルシステム (VFS) と名前空間

### UNIX VFS と「すべてはファイル」
- **VFS (Virtual File System)**: 多様なファイルシステム（ext4, FAT, NFS, procfs 等）の差異を吸収し、`open / read / write / close / stat / readdir` という統一システムコールインターフェースを提供する抽象層（`superblock`, `inode`, `dentry`, `file` オブジェクト）。
- **FUSE (Filesystem in Userspace)**: カーネル内の VFS リクエストをユーザー空間のプロセスに転送して処理させる仕組み。これにより、リモート API や Git リポジトリ、暗号化ストレージ、仮想ビューなどを通常のファイルシステムとしてマウントできる。

### Plan 9 from Bell Labs / Inferno（名前空間の極致）
UNIX の「Everything is a file」を徹底し、ネットワーク分散環境へ再設計した OS。
- **統一プロトコル 9P (Styx)**: ローカルファイルも、ネットワーク越しのファイルも、プロセス情報（`/proc`）も、GUI ウィンドウ（`/dev/draw`）も、ネットワークスタック（`/net`）も、すべて **9P プロトコルを話すファイルサーバー** として公開される。
- **Per-process Private Namespaces（プロセスごとのプライベート名前空間）**:
  - グローバル単一のルート `/` は存在しない。各プロセス（グループ）が自分専用のファイルツリービュー（名前空間）を持つ。
  - `bind` / `mount` によって、あるサービスやローカルディレクトリを自分の空間の任意のパスに自由にマウント・上書き・合成（Union Directory）できる。
  - 例: リモートの別マシンの `/net` を自分の `/net` にマウントすれば、そのままリモート側のネットワーク経由で通信できる（VPN や特殊 API 不要）。
- **エージェント設計への強力な示唆**: プロセス（サブエージェント）ごとに見えるファイルツリーやツール群（ファイルサーバーとして表現された機能）を自在に構成・隔離・差し替えできる。

### GNU Hurd Translators
- ファイルシステムのディレクトリやファイルノードに「Translator（変換プログラム）」を紐づけ、アクセス時に動的にコンテンツを生成・変換する機構（FUSE の先駆的な思想）。

## 4.3 トランザクション・階層化・ロールバック

### Union / Overlay ファイルシステム
- **OverlayFS / AUFS**:
  - **Lowerdir（読み取り専用のベース層）** の上に **Upperdir（書き込み用の差分層）** を重ね、ユーザーからは統合された 1 つのディレクトリツリー（Merged）に見せる。
  - 既存ファイルの変更時は Lower から Upper へコピーしてから書き換える（CoW）。削除は Upper に **Whiteout ファイル** を置くことで表現。
  - **利点**: ベース環境を一切汚さず実験でき、Upperdir を丸ごと検査して「何が変更されたか（Diff）」を正確に抽出でき、不要なら Upperdir を捨てるだけで完全ロールバックできる。

### CoW ファイルシステムとスナップショット
- **ZFS / Btrfs / APFS / HAMMER**:
  - データブロックを上書きせず常に新しい空き領域に書き込み、メタデータツリー（B-tree）のルートポインタを原子的に差し替える（**Copy-on-Write ツリー**）。
  - **スナップショット**: ある時点のルートポインタを保持しておくだけで、O(1) でゼロコピーの完全な静止スナップショットが取れる。
  - **サンドボックス・クローン**: スナップショットから書き込み可能なクローンを分岐させ、試行錯誤して成功したら反映・失敗したら破棄する。

### ジャーナリング・WAL・トランザクション FS
- **WAL (Write-Ahead Logging) / Journaling (ext4, NTFS)**: 変更内容を先にログ（ジャーナル）に書き出してから本体を更新し、クラッシュ時に一貫した状態へ復旧（Redo/Undo）する。
- **Shadow Paging / トランザクション的ファイル操作**: 複数のファイル操作を `begin_tx()` 〜 `commit()` / `abort()` で括り、途中失敗時にすべてなかったことにする（Windows TxF、データベースエンジン、Btrfs のトランザクション ioctl 等）。

### イミュータブル / 宣言的 OS（NixOS, Guix, ostree / Silverblue）
- **思想**: OS の状態（パッケージ、設定ファイル）を「既存の環境への破壊的インプレース更新」で変えるのではなく、**宣言的仕様から新しい世代（Generation）を純粋関数的にビルドし、シンボリックリンク（またはデプロイメントツリー）を原子的に切り替える**。
- **利点**:
  - どの変更も「世代番号」として履歴が残り、1コマンド・再起動 1 回で前の世代へ確実にロールバックできる。
  - 環境の再現性が保証される。
- **バージョン管理 OS との親和性**: ファイルシステムの変更セットを Git コミットや Ostree コミットのように扱うことで、「試行 → 差分確認 → マージまたは破棄」のワークフローが自然になる。
