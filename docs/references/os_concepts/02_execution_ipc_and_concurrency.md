# 2. 実行モデル・特権分離・IPC・監視と回復

プロセスやタスクをどう表現し、どう協調させ、異常時にどう立て直すかについて、OS が蓄積してきた機構を整理する。

---

## 2.1 実行単位と並行モデル

### プロセス vs スレッド vs 軽量実行単位
- **プロセス (Process)**: 独立したアドレス空間、ファイル記述子テーブル、権限（UID/Capability）を持つ **「資源所有と隔離の単位」**。
- **スレッド (Kernel Thread / OS Thread)**: プロセス内のアドレス空間と資源を共有し、レジスタとスタックのみを独立させた **「CPU スケジューリングの単位」**。
- **グリーンスレッド / コルーチン / ファイバ (User-space Scheduling)**:
  - **N:1 モデル**: ユーザー空間スケジューラが 1 つの OS スレッド上で多数のタスクを協調的（あるいはプリエンプティブ）に切り替える。
  - **M:N モデル**（Go goroutine, Erlang BEAM プロセス, Tokio 等）: 多数の軽量タスク（M）を少数の OS スレッド（N）に割り当てる。コンテキストスイッチが安価で数万単位の並行性を扱える。
  - **共有なし隔離タスク（Erlang BEAM プロセス / Dart Isolate）**: メモリを共有しない軽量実行単位。プロセス並みの論理隔離を、OS プロセス生成のコストなしで実現する。

### 静的タスク構成 vs 動的プロセス生成
- **POSIX `fork()` + `exec()`**: 親のコピーを作ってから別プログラムに差し替えるモデル。柔軟だが、グローバル状態や不要な fd の継承がセキュリティ・整合性上の罠（fd leak, multi-thread fork 問題）になりやすい。
- **`posix_spawn` / `CreateProcess` (Windows)**: 生成時に必要な引数・環境・継承ハンドルを明示的に渡す生成モデル。状態汚染を防ぐ上でクリーン。
- **静的タスク構成（Hubris / OSEK / RTOS）**: 起動・ビルド時に全タスクと通信経路を固定する。動的生成によるメモリ枯渇・タスク爆発（fork bomb）を構造的に不可能にする。

## 2.2 保護リングと特権分離

### ハードウェア保護リング（Protection Rings）
- **Multics（8リング: Ring 0〜7）**: ハードウェア支援により、最も信頼されたカーネル（Ring 0）、OS サービス（Ring 1-2）、共有ライブラリ（Ring 3）、一般アプリ（Ring 4+）、デバッグ対象・非信頼コード（外周リング）のように多段階の信頼階層を表現した。ゲート機構（Call Gate）を通じた段階的昇格が可能だった。
- **x86（Ring 0〜3）/ ARM（EL0〜EL3）**: 現代の汎用 OS は複雑さと性能の理由から実質的に **2段階（Ring 0: カーネル / Ring 3: ユーザー）** しか使わない（仮想化でハイパーバイザ用 Ring -1 / EL2、ファームウェア用 EL3 を使う）。
- **多段階リングの教訓**:
  - 抽象モデルとしては「権限レベルごとにゲートを設け、外側からの要求はゲート（承認・検証）を通す」という考え方が極めて強力。
  - 一方、現代ではリング番号の多段化よりも **プロセス単位の最小権限＋ケーパビリティの組み合わせ** の方が柔軟で合成しやすいとされている。

### 特権分離（Privilege Separation）パターン
モノリシック OS 上のアプリケーションやデーモンでも、OS のプロセス境界を使って内部を「小さな特権モニター＋非特権ワーカー」に分割する設計が確立されている。
- **OpenSSH**: 認証や秘密鍵アクセスを行う最小限の **Monitor プロセス** と、外部からの入力（ネットワークパケットのパース等）を扱う **非特権サンドボックスプロセス** に分離。
- **qmail / Postfix**: 受信・キュー管理・ローカル配送・リモート配送など役割ごとに独立プロセス・独立権限で実行。
- **Chromium ブラウザ**: Browser プロセス（特権・UI・ストレージ窓口）と Renderer プロセス（非信頼 Web コンテンツ実行、厳格サンドボックス）、Network/GPU プロセスに分離し、IPC（Mojo）で通信。

## 2.3 システムコール機構の進化

### 同期システムコール（Trap / `syscall`）
- ユーザー空間からレジスタに引数とシステムコール番号をセットし、CPU 命令（`syscall` / `svc`）で特権モードに遷移。カーネルが検証・処理して戻る。
- **vDSO (Virtual Dynamic Shared Object)**: 時刻取得（`gettimeofday`）など、特権遷移が不要で読み取り専用の情報は、カーネルがメモリページをユーザー空間に共有マップし、システムコール遷移自体を省略する。

### 非同期・バッチ型システムコール（`io_uring`）
- **背景**: Specter/Meltdown 対策以降、システムコール毎のモード切替コストが増大。
- **構造**: ユーザー空間とカーネル空間で 2 つのリングバッファ（**Submission Queue: SQ** と **Completion Queue: CQ**）を共有する。
- **利点**: 複数の I/O 要求を SQ に積んで 1 回の通知（あるいはポーリング）でまとめて処理し、結果を CQ から非同期回収できる。システムコールのバッチ処理・ゼロコピー・パイプライン化が可能。

## 2.4 プロセス間通信 (IPC) の諸形態

| IPC 方式 | 代表例 | 特徴・利点 | 注意点・トレードオフ |
| :--- | :--- | :--- | :--- |
| **バイトストリーム** | UNIX Pipe, FIFO, Socket | 単純で汎用、`cat \| grep` 的合成に強い | メッセージ境界がなく、構造化データのパースが必要 |
| **メッセージキュー / メールボックス** | POSIX MQ, Mach Port, System V MQ | 非同期にメッセージを積める、受信側が自分のペースで処理 | キュー溢れ・バックプレッシャ制御・カーネルメモリ消費の管理が必要 |
| **同期ランデブー型 IPC** | L4, QNX (`MsgSend`/`Reply`), Hubris | **キューを持たない**。送信側は相手が応答するまでブロック。メモリ枯渇やメッセージスパムによる **障害増幅 (Fault Amplification) を防ぐ** | 呼び出し順次第でデッドロックの危険。並列性を保つにはワーカープール設計が必要 |
| **双方向チャネル＋権限転送** | Zircon Channel, UNIX `SCM_RIGHTS`, Chromium Mojo | データだけでなく **ハンドル/FD（ケーパビリティ）をそのまま転送** できる | 転送後のプロトコル（状態遷移）の整合性設計が重要 |
| **共有メモリ＋通知** | `shm`, Futex, `io_uring`, L4 Flexpage | 大容量データのゼロコピー転送 | 競合状態・キャッシュ一貫性・相手がメモリを書き換えるリスク（TOCTOU） |
| **構造化 RPC / IDL** | Fuchsia FIDL, Android Binder, D-Bus, Singularity Contract | 型付きインターフェース定義からスタブ生成。非互換や境界エラーを防止 | スキーマ進化・バージョニングの管理 |

### TOCTOU（Time-of-Check to Time-of-Use）問題
共有メモリやパス文字列を引数にするシステムコールでは、「カーネルが安全性を検証した直後に、ユーザー空間の別スレッドがメモリやシンボリックリンクを書き換える」攻撃（TOCTOU）が起こり得る。対策としては：
- 引数をカーネル側（または安全な境界内側）にコピーしてから検証・実行する（値渡し・メッセージパッシング）。
- パス文字列ではなく、検証済みの不変ハンドル/ディレクトリ FD（`openat` ファミリー）を使う。

## 2.5 Actor モデルとプロセス監視・異常系

### シグナル（POSIX Signals）とその限界
- `SIGTERM`（終了要求）, `SIGKILL`（強制終了）, `SIGSTOP`/`SIGCONT`（一時停止/再開）, `SIGCHLD`（子プロセス状態変化通知）。
- **限界**: 非同期割り込みハンドラ内では使える関数が極端に制限される（Async-signal-safe 問題）、ペイロードをほぼ運べない、レースコンディションを起こしやすい。そのため現代的な OS では `signalfd`（Linux）、`kqueue`（BSD）、あるいはイベントチャネル/ポートへの統合が進んでいる。

### 例外ポート・フォールト委譲（Mach / Zircon）
- プロセス内で不正アクセスやクラッシュが起きたとき、カーネルが即死させるのではなく、登録された **監視プロセス（Exception Channel / Port）へ「例外メッセージ」を送信** して判断を仰ぐ仕組み。デバッガやクラッシュレポータ、自己修復マネージャーが統一的に扱える。

### Supervisor ツリーと自己修復（"Let It Crash"）
OS やランタイムが障害を「予防する」だけでなく「前提として素早く隔離・回復する」設計。
- **Erlang / OTP Supervisor**:
  - プロセスは一切状態を共有せず、メールボックスのみで通信。
  - エラーが起きたら無理に内部で修復せずクラッシュさせ、親の **Supervisor** が「1対1再起動（One-for-One）」「全道連れ再起動（One-for-All）」「以降を巻き添え再起動（Rest-for-One）」や再起動レート制限（MaxR/MaxT）に基づき回復する。
- **MINIX 3 Reincarnation Server**:
  - ユーザー空間ドライバへ定期的にハートビートを送り、応答がない・異常終了した場合はそのドライバだけを再インスタンス化する。
- **Hubris Supervisor**:
  - 固定タスク群の監視役として特別な非特権タスク `jefe` (Supervisor) を置き、他タスクの障害記録とリセット方針を司る。
- **systemd / launchd**:
  - サービスの依存関係管理、ソケットアクティベーション（要求が来るまでプロセスを起動しないオンデマンド起動）、自動再起動、cgroup 単位での一括クリーンアップ（孤児プロセスを残さない）。
