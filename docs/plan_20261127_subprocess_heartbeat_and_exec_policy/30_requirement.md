## 2. 適用制約・非機能・検証範囲の方針

1. **非機能の追加要求**: 利用者からスループット・レイテンシ SLO・カバレッジ率等の新規数値目標は求められていないため、**合意にない数値目標や不要な品質水準は新設しない**。
2. **検証の強さと Evidence class**:
   - 本環境の Windows 11 + Dart SDK + Jujutsu (`jj`) 環境において、`REQ-01`〜`REQ-06` はすべて自動テスト・ビルド確認（`E1`）、実プロセス／ACP 実行観測（`E2`）、およびコード境界照合（`E3`）によって直接検証可能であり、`EX`（直接確認不能）を前提とする要求はない。
   - 長時間上限（60 分壁時計・5 分既定 Heartbeat）については、実時間で 60 分待機するテストを行う必要はなく、定数・境界バリデーション確認と、短縮パラメータ（`maxWallTimeMs` / `heartbeatTimeoutMs` / `sys_wait.timeoutMs` に数百 ms〜数秒を指定）を用いた実タイマー発火・非発火テスト（`E1` / `E2`）によって検証する。
3. **既存アーキテクチャ制約の維持**:
   - `packages/agent_runtime/lib/src/prompts/agent_prompts.dart` および `process_runner.dart` は引き続き `dart:io`・`agent_drivers`・`http` に依存しない純粋構成を維持する。
   - `.agent_os/` 配下（`exec_policy.json`, `models.json`, `.env`, 監査ログ等）の `PROTECTED_INTERNAL_PATH` 保護を維持する。
   - 子プロセスからの更なる `sys_spawn` / `sys_wait` 禁止（深度 1 固定）を維持する。
4. **対象外**: [20_app_requirement.md](./20_app_requirement.md) §4.2 記載の項目（Gitea Issue #2、シェル解禁、`mise` 等の専用特別ガード、設定ファイルの動的ホットリロード、ターン跨ぎ孤児子プロセス存続）は今回の対象外とする。

## 4. 通常設計判断に委ねる事項（`40_specification.md` 対象）

以下は要求の目的・範囲・合意条件を変えない技術設計事項として、後続の `fm-dev-architect` が `40_specification.md`（および必要に応じた `42_spec_*.md`）で具体化する：
1. `.agent_os/exec_policy.json` の具体的な JSON スキーマ構造（ルール配列フィールド名、コマンド名・サブコマンド／引数プレフィックス・パス引数検証有無・ルール別 `maxTimeoutMs` 等の表現形式）。
2. `sys_wait` の返却 JSON ペイロードおよび `_fm_agent_os/processes` の具体的なフィールド名・型定義（既存 `children` との後方互換を保った `timedOut` / `running` / `heartbeat` オブジェクト構造）、ならびに `sys_wait.timeoutMs` の許容上限値（現行 `300,000ms` 維持または引き上げ）。
3. `HEARTBEAT_TIMEOUT` 終了時の具体的な `SyscallErrorCode`（`ETIMEDOUT` または `EDQUOT` 等）、`exitCode`、および Supervisor `RestartStrategy.onFailure` における再試行可否の扱い。
4. 追加許可コマンド実行時における `/workspace/...` 仮想パス引数のホスト相対パス解決ルール（`Win32JobExecDriver._buildSpawnPlan` と `SysExecClassifier` の連携）および Windows 実行ファイル解決の細部。
5. `AgentPrompts` および `Win32JobExecDriver.toolSchemas` へ設定済み許可コマンド概要を注入する純粋 API シグネチャ（KV プレフィックスキャッシュ安定性を損なわない決定的フォーマット）。
